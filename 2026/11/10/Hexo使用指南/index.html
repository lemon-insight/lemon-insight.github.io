Hexo 静态博客完整指南：从安装到部署

Lemon 柠檬 Lv2

Hexo 是基于 Node.js 的静态博客框架：用 Markdown 写作，用主题控制外观，构建时生成纯静态文件。它不需要数据库和后端服务，部署成本低、访问速度快，适合个人博客、项目文档和知识库。本文以 Hexo 7.x 为例，从环境准备讲到多平台部署，面向第一次接触 Hexo 的读者。

一、Hexo 的核心特性

1. 静态站点生成

Hexo 把 source/ 中的 Markdown、themes/ 中的模板和 _config.yml 中的配置，在构建阶段编译成 public/ 下的 HTML、CSS、JavaScript 和图片。浏览器访问时不需要 Node.js、数据库或后端进程，因此可以托管在 GitHub Pages、对象存储或任意 CDN 上。

这种“内容与展示分离”的结构有两个直接好处：源文件都是可版本管理的文本，迁移和备份简单；线上只暴露静态文件，没有数据库注入、服务端漏洞之类的风险。

2. 高性能渲染

生成过程在 Node.js 中完成：渲染器把 Markdown 转成 HTML，生成器把文章、分类、标签、归档组织成路由，主题模板再把它们套进布局。Hexo 使用内存数据库和 db.json 缓存，重复生成通常比首次快；配合 hexo generate --watch，写作时可以持续构建、刷新页面即可看到变化。

对常规博客规模，生成通常在秒级到几十秒级，具体取决于文章数量、主题复杂度和图片处理量。文章很多时，瓶颈往往在主题渲染和图片，而不是 Markdown 解析。

3. 插件生态

Hexo 的功能按插件拆分：hexo-renderer-* 负责渲染 Markdown、模板和样式，hexo-generator-* 负责生成首页、归档、分类、标签、RSS 和站点地图，hexo-deployer-* 负责把产物推到不同平台，hexo-filter-* 负责处理内容。插件通过 npm 安装，在 _config.yml 中配置，按需启用。

4. Markdown 与 Front-matter

文章用 Markdown 编写，支持标题、列表、表格、代码块、图片和引用；Front-matter 放在文件开头，用来声明标题、日期、分类、标签等元数据。<!-- more --> 可以控制首页摘要，代码高亮由渲染器或主题配置决定。

5. 一键部署

hexo deploy 会调用部署插件，把 public/ 推送到目标平台。常见方式包括 Git 部署到 GitHub Pages、GitLab Pages，或由 Vercel、Netlify、Cloudflare Pages 监听仓库自动构建，也可以用 rsync、SFTP 推到自有服务器。

6. 主题系统

主题决定布局、配色、导航、评论、搜索和响应式行为。Hexo 主题既可以是 themes/ 下的目录，也可以是 npm 包；主题配置通常放在 _config.<theme>.yml，与站点配置分离，升级主题时不容易冲突。

二、环境准备与初始化

1. 安装 Node.js 与 Git

Hexo 7 建议使用 Node.js 18 LTS 及以上，推荐 20 或 22 LTS。安装后检查：

Node 版本过低会出现语法错误或依赖安装失败；版本过高也可能遇到原生模块兼容问题。需要切换版本时，优先使用 nvm、fnm 这类版本管理工具，而不是反复卸载重装。

2. 安装 Hexo CLI

如果全局安装提示权限不足，建议用 nvm 管理 Node，避免直接用 sudo npm install -g 污染系统目录。也可以不全局安装，改用 npx hexo-cli。

3. 创建站点

hexo init 会复制官方脚手架并安装基础依赖；再执行一次 npm install 是安全的，能确保依赖完整。

目录结构如下：

路径 作用
_config.yml 站点配置
package.json 依赖与脚本
scaffolds/ 新建文章、页面的模板
source/_posts/ 文章正文
source/_drafts/ 草稿
source/ 页面、图片等资源
themes/ 主题目录
public/ 生成的静态文件
db.json 生成缓存，可删除
.deploy_git/ Git 部署缓存，使用 deployer-git 时出现

三、写作：文章、页面与草稿

1. 新建文章

文件生成在 source/_posts/我的第一篇文章.md。文件名会影响默认链接，建议使用英文或拼音，避免空格和特殊字符；标题可以在 Front-matter 里单独写中文。

2. Front-matter 常用字段

字段 说明
title 文章标题
date 发布时间，未来时间默认不发布
updated 更新时间
categories 分类，可写多个
tags 标签，可写多个
permalink 自定义文章链接
published 设为 false 可暂不发布
comments 是否启用评论，取决于主题
top 置顶，取决于主题是否支持

YAML 对缩进敏感，列表项前的两个空格不要漏。分类和标签不要写成逗号分隔的字符串，除非主题明确支持。

3. 摘要与图片

在正文中单独一行写 <!-- more -->，它之前的内容会作为首页摘要，之后的内容在文章页展开。

图片可以放在 source/images/，用 /images/foo.png 引用；也可以在 _config.yml 中开启 post_asset_folder: true，让每篇文章生成同名资源目录，再用标签引用：

前一种方式简单，适合图片少的站点；后一种方式便于文章整体迁移。

4. 新建页面

生成 source/about/index.md，在主题配置的菜单中加入 about: /about/ 即可。页面没有发布日期，适合“关于”“友链”“归档说明”这类固定内容。

5. 草稿

草稿保存在 source/_drafts/，默认不生成；hexo publish 会把它移到 _posts/ 并参与构建。

四、配置详解

1. 站点配置 _config.yml

最常改的字段：

键 作用 示例
title 站点标题 我的博客
subtitle 副标题 记录与分享
description 站点描述 一个静态博客
keywords SEO 关键词 Hexo, 博客
author 作者名 Lemon
language 语言 zh-CN
timezone 时区 Asia/Shanghai
url 站点完整地址 https://example.com
root 站点根路径 /
permalink 文章链接格式 :year/:month/:day/:title/
theme 主题名称 redefine
post_asset_folder 是否启用文章资源目录 true
future 是否发布未来日期的文章 false
syntax_highlighter 代码高亮器 highlight.js

url 和 root 必须与最终访问地址一致。用户站点通常是 url: https://username.github.io、root: /；项目站点则是 url: https://username.github.io/project、root: /project/。这两个值写错，部署后常见表现是 CSS、JS 和图片全部 404。

3. 常用插件

搜索、评论、图片懒加载、数学公式等插件按需安装。插件版本要与 Hexo 大版本匹配；升级 Hexo 前先看插件的兼容说明。

五、主题安装与定制

选择主题时看三点：是否兼容当前 Hexo 版本、是否持续维护、文档是否完整。安装后先按主题文档配置菜单、社交链接、头像、横幅、评论和搜索，再考虑改样式。常见主题包括 Landscape（默认）、NexT、Fluid、Butterfly、Redefine，不同主题的配置项差异很大，以主题文档为准。

定制时尽量把自定义内容放在站点侧：source/_data/、source/css/、source/js/，或主题提供的自定义配置项。这样升级主题时只需处理少量冲突。升级前备份 _config.<theme>.yml 和自定义样式。

六、生成与本地验收

hexo clean 删除 public/ 和 db.json；主题、配置大改后先清理，能避免旧缓存导致的“改了没生效”。hexo generate 输出到 public/；加 --watch 可以持续监听源文件。

部署前至少检查：首页、文章页、分类页、标签页、归档页、404 页面、图片、代码高亮、移动端布局、暗色模式，以及 RSS 和 sitemap 是否能访问。

七、部署到多个平台

1. GitHub Pages：源码与部署分离

推荐把源码放在一个仓库（例如 blog-source），把生成的静态文件放在 username.github.io 仓库。这样源码历史干净，Pages 仓库只保留构建产物。

顺序很重要：先提交并推送源码，再执行部署。否则部署提交会早于源码提交，历史顺序会变得难以对应。部署完成后，到仓库的 Settings → Pages 确认分支和目录。

如果是项目站点（https://<username>.github.io/<project>），把 url 设为项目地址，root 设为 /<project>/，部署分支通常改用 gh-pages。

自定义域名时，在 source/ 放一个 CNAME 文件，内容为域名；DNS 配置 CNAME 指向 <username>.github.io，或在根域名使用 A 记录。最后在 Pages 设置中开启 HTTPS。

如果 Pages 从分支部署，建议在 source/ 放一个空的 .nojekyll 文件，避免 GitHub 的 Jekyll 处理忽略以下划线开头的目录。

2. GitHub Actions

也可以让 GitHub 在每次 push 时自动构建并发布，仓库只存源码：

如果 npm ci 报错，通常是仓库里没有提交 package-lock.json；改用 npm install，或先本地生成并提交锁文件。然后在 Settings → Pages 中选择 GitHub Actions 作为来源。

3. Vercel、Netlify 与 Cloudflare Pages

这三个平台都支持连接 Git 仓库、自动安装依赖并构建。通用配置如下：

平台 构建命令 输出目录
Vercel npx hexo generate public
Netlify npx hexo generate public
Cloudflare Pages npx hexo generate public

安装命令用 npm install 或 npm ci，Node 版本选 20 LTS。若主题以 Git 子模块方式放在 themes/，要确保平台拉取子模块；使用 npm 主题可以避开这个问题。

5. 其他方式

自有服务器可以用 rsync 或 SFTP 部署器，把 public/ 同步到 Web 根目录；高并发场景可以把 public/ 上传到对象存储，再套 CDN。无论用哪种方式，部署前都执行 hexo clean && hexo generate，保证产物可复现。

6. 部署检查清单

  • url 和 root 与最终访问地址一致
  • 部署前执行过 hexo clean
  • 源码已经提交并推送
  • 自定义域名有 CNAME，分支部署有 .nojekyll
  • HTTPS 已开启
  • CDN 或浏览器缓存已刷新
  • 首页、文章、分类、标签、归档、404、图片和 RSS 均可访问

八、常见问题

问题 原因与处理
hexo: command not found 全局 bin 不在 PATH；用 npx hexo，或重装 Node 后重开终端
4000 端口被占用 hexo server -p 5000 换端口
改了主题没生效 执行 hexo clean，确认 theme 名称与目录或包名一致
部署要求输入密码 GitHub 已不支持密码推送；改用 Personal Access Token 或 SSH
spawn git ENOENT Git 未安装或不在 PATH
图片 404 路径或大小写错误；Linux 区分大小写，统一用 /images/...
未来日期的文章不显示 future 默认为 false；调整日期或改为 true
部署后 CSS/JS 404 url 或 root 配错，尤其是项目站点
自定义域名被覆盖 CNAME 要放在 source/，不要只放在 public/
.deploy_git 冲突 它是部署缓存，可删除后重新部署
页面内容陈旧 删除 db.json 或执行 hexo clean 后重新生成

九、命令速查

命令 作用
hexo init <dir> 初始化站点
npm install 安装依赖
hexo new "标题" / hexo n 新建文章
hexo new page about 新建页面
hexo new draft "标题" 新建草稿
hexo publish "标题" 发布草稿
hexo server / hexo s 启动本地服务器
hexo generate / hexo g 生成静态文件
hexo deploy / hexo d 部署
hexo clean 清理 public/ 和 db.json
hexo list post 列出文章
hexo version 查看版本

十、推荐工作流

  1. 写作：hexo new 创建文章，Markdown 编辑，hexo server 本地预览。
  2. 提交源码：git add、git commit、git push，确保源文件先进入远端。
  3. 构建部署：hexo clean && hexo generate && hexo deploy。
  4. 线上验收：检查首页、文章、图片、RSS 和自定义域名。
  5. 定期维护：npm outdated 查看过期依赖，升级 Hexo 大版本前阅读变更说明并备份主题配置。

源码仓库建议提交 package-lock.json，用 .nvmrc 固定 Node 版本，并把 node_modules/、public/、.deploy_git/、db.json 排除在版本控制之外。源码、主题配置和自定义资源都在 Git 里，才算真正可恢复。
